# User Guide — End-User Documentation

## Purpose and audience

A user guide helps end users (non-tech users) accomplish goals with the software. The audience is people who use the product — not people who built it. Write for their level of technical familiarity, not yours.

Good user documentation reduces support tickets, accelerates adoption, and builds user confidence. Bad documentation frustrates users and damages trust in the product.

## When to write a user guide

- Launching a new feature or product
- Feature behavior has changed and existing users need to adapt
- Support team is answering the same question repeatedly
- Onboarding new users to a complex workflow
- Compliance or audit requires documented procedures
- Step by step instruction and sample

## Key sections

**Introduction**
What does this feature or product do, and who is it for? One short paragraph. Do not explain how it works internally.

**Prerequisites**
What does the user need before they start? Account type, permissions, data that must exist, software to install. List these upfront so users do not discover them mid-task.

**Getting started**
The fastest path to the user's first success. Keep this section short and linear — one task, one goal. Complex variations come later.

**Step-by-step instructions**
Each task gets its own section with a clear title ("How to export a report", not "Export"). Format as numbered steps. One action per step. Include what the user should see after each action so they know they're on track.

**Screenshots and examples**
Use screenshots to show the UI at key decision points, not every click. Annotate with callouts when the target element is not obvious. For data-entry tasks, show an example of correctly filled values.

**Configuration and settings**
If users can customize behavior, document every option: what it does, what the default is, and when to change it.

**Troubleshooting**
Common errors and their solutions, written in terms of what the user sees ("If you see the message 'Permission denied'…"), not what caused them internally. Include "if this doesn't work, contact support" with the right channel.

**FAQ**
3–8 questions that surface frequently. Prioritize questions that reveal misunderstandings about how the feature works, not just missing instructions.

**Reference**
Field-level descriptions, keyboard shortcuts, limits (max file size, character limits), and other reference data users need to look up occasionally.

## Writing discipline

- Use second person: "You can…", "Select…", "If you see…". Avoid "the user should".
- Use imperative for instructions: "Click Save", not "You should click Save" or "Save can be clicked".
- One task per section. Long multi-task sections lose users who are only trying to do one thing.
- Write for scanning, not reading. Use headings, numbered lists, and callout boxes. Dense paragraphs get skipped.
- Avoid jargon the user would not know. When a technical term is unavoidable, define it inline on first use.
- Test the instructions yourself before publishing. Follow them exactly as written in the actual product — documentation that has never been tested is almost always wrong in at least one step.
- Date-stamp or version-stamp the document so users know whether it matches the software they are using.
- Document style must be simple for non-tech user to read and follow the instruction
- The Instruction must be detail and step by step instruct
